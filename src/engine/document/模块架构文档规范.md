# 模块架构文档规范

## 用法

模块重构时，先在模块旁编写同名md作为架构设计文档。
模块架构文档只描述模块自身的直接职责、直接依赖和直接产出。

## 文档内容结构

每份模块架构文档只保留以下内容：

```markdown
# 模块名

## 模块职责

## 理想结构

## 关键设计决策
```

### 模块名

使用模块的领域名称，保持与代码模块和现有文档的称呼一致。

### 模块职责

说明模块的核心职责和边界。建议列出 1-5 项职责。

### 理想结构

每个方法都必须使用完整 JSDoc。函数缺少任意参数的 @param、缺少 @returns 或缺少抽象实现步骤，都视为文档不合格。
正文中的能力说明使用领域概念。只有接口草案或代码结构示例使用实际代码对象名称；代码对象名称不替代正文中的领域概念。

### 关键设计决策

记录已经确认、会影响模块边界或后续实现方向的决策。

每项决策说明：

- 设计理念（比如可维护性大于可扩展性、优雅性大于完善性）
- 为什么

## 表述规则

使用直接的职责陈述：

```markdown
World 管理模拟时间。
GameEngine 驱动 World 执行离散模拟。
输入通道记录当前控制目标。
输出协议描述 World 的稳定资源类型。
```

用职责归属表达边界，避免使用二元对立式表述。每项内容集中说明当前模块承担的责任、依赖关系和约束。
不进行反向描述，比如：不XXXX。

正文优先使用中文领域概念，不直接使用具体英文属性名、方法名或类型名代替概念。例如使用“目标成员标记”“帧序号”“模拟时间”“输入通道”“输出协议”，而不是在普通叙述中直接写 `targetMemberId`、`tickIndex`、`simulationTimeMs`。接口草案中的代码名称可以保留，但应先用中文说明其职责。

## 长度建议

单份模块架构文档出理想结构外，建议控制在 200-400 字：
协议和跨模块总览可以适当增加篇幅，但仍遵守以上文档类型边界，不将实施细节写入模块架构文档。
