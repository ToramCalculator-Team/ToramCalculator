# Engine — 代理工作指南

## 通信机制角色

词汇见 [CONTEXT.md](CONTEXT.md)。本节只规定约束：

- 引擎的通信机制由三类构成：事件总线承担 GameReactor 内部的同步事实通知；网络端口承担反应器之间的数据依赖；宿主接入的数据消费端承担网络外部对模拟的读取与记录。新增通道时，先写明它属于哪一类。
- 端口表达数据依赖，观察者表达呈现与记录需求。端口形状在装配期固定；观察者数量与周期由消费者声明决定，宿主在运行期 attach/detach。
- 宿主提供环境：唯一时钟与输入通道。宿主通过时钟位置与输入快照影响游戏系统，时钟不前进时系统静止。
- 事件总线是 Reactor 内部组件通信设施，也是事件源的通知来源。事件输出过滤器作为事件总线的订阅者，位于 Reactor DAG 之外。
- 只有需要参与网络反应的数据才通过 Reaction 和端口发布。

派生信号一律视为喂入上述角色的适配器，不是独立机制：

- 状态变化、属性阈值穿越 → 发布到参数端口，或按 `Action.schedule` 调成 tag 上的事件。
- 未来时刻的效果或状态变化 → `Action.schedule` 调度，到期执行后按需发布事件。
- 外部控制器意图 → 经输入端口快照进入网络，由游戏层按目标身份处理。

**断点必须是 tag**：分段切换、buff 到期、阈值穿越这些改变连续量参数的时点，能解析求出的都要调度成 tag。时点不是 tag 时，参数会晚于事件生效，采集端在区间内只能用旧参数外推。

**跨 tag 不读端口**：端口值只在写入的那个 tag 上可见，需要跨 tag 持续可见的连续量用参数端口发布，采集器读参数并用状态方程外推。

**物理事件读取环境时钟**：物理时间就是 GameSystem 所在虚拟世界的真实时间，唯一来源是宿主的环境时钟。

网络内节点之间相互影响的写入按因果先后分属不同微步，由端口依赖或微步推进决定，而不是靠遍历顺序。微步只用于真正需要区分因果的场合。

## 线程间通道

引擎与主线程之间的数据面是**输入缓冲加每个采集器一个输出缓冲**：

- **输入端口**：控制侧写自己的槽位，网络按 tag 读出输入快照。槽位内分状态区（方向、步态、强度）与命令区（离散动作），同槽位共用一个发布号。
- **输出缓冲区**：每个采集器一个。采集器持有选择字段、采样周期、容量与满了怎么办这四项配置，按自己的周期写入自己的缓冲区。

一个采集器一个缓冲区的理由是发布号粒度：全局单发布号会让 10 秒采集与 60Hz 呈现共用一个发布号，必然有一个被迫降频。

缓冲区内的发布规则：连续量允许读取方跳过中间提交，离散事件必须逐次消费，容量不足时显形失败而不是静默覆盖。

逻辑时刻是唯一的顺序轴，微步表达同一时刻内的先后。事件不携带墙钟时间偏移。

生命周期命令与结果、一次性变长查询、运行故障走消息通道。生命周期由同一份状态机定义生成控制器端与执行端两个 actor，命令与结果按 correlationId 关联；宿主执行端对命令做前置断言。

**观察者由宿主按声明创建**：宿主在 attach 时按消费者声明创建采集器、事件过滤器与记录器，返回句柄，统一处理 detach、失败与诊断。ready、running、paused 开放 attach/detach；attach 立即采样首帧；选择变化表达为 detach 加 attach，布局固定。

**布局单源、双侧校验**：SAB 由主线程创建；Worker 用共享 codec 派生并校验布局；布局带版本号。采集器声明中，内置内容用生成目录加泛型 builder（声明即类型），玩家内容用 zod sample schema，统一 wire 声明。

过线的只能是设备无关、已定帧、可重放的语义值：方向是世界方向，步态是语义标签（走 / 跑），命令不带墙钟时间。

引擎通过声明与缓冲区通信：调用侧提交声明，Worker 侧按声明创建观察者；网络与宿主不接收外部回调。观察者按消费者声明创建，消费者数量可以为零，消费者配置只影响产出，不影响模拟结果。

## 引擎边界

引擎只描述通用机制：反应器网络、时间、输入、观察者机制、属性求值、计算管线、行为运行时、事件总线、网络外事件输出、xstate 运行时能力、检查点与记录。成员、区域、世界等游戏概念属于游戏层；GameReactor 组合引擎能力与游戏规则。引擎模块与文档不定义这些游戏概念。

第一版状态机运行时用 xstate v5。GameReactor 直接持有同步 xstate actor；actor 接收内部事件并提交意图，不映射 Reactor 输入输出端口。`invoke`/`spawn` 禁用，`after` 编译成 `Action`，动作只提交意图。玩家内容用 schema 校验，内置内容用生成的静态类型。

## 文档与 ADR

引擎词汇见 [CONTEXT.md](CONTEXT.md)：术语定义与禁用同义词在那里维护，本节与模块文档不重复定义。

引擎设计意图通过模块旁的模块架构文档、`src/engine/document/` 和 `docs/decisions/` 保留。工作时读取相关文档；存在候选方案与实质权衡的决策新增项目级 ADR，概念迭代与职责重划直接写入模块架构文档与 L1 概览；历史叙述文档只作为历史快照读取。

**模块的职责不应该耦合他的上级模块。** 模块架构文档只描述该模块自身的职责、直接依赖、直接产出与实现方式，不描述调用它的上级模块、同级模块的分工或全局所有权划分；

文档与接口草案只保留当前需要的能力，不预留推测性参数或抽象。

当前 L1 概览见 `src/engine/document/引擎架构设计.md`；`src/engine/document/架构设计说明概要.md` 保留为旧帧模型的历史快照。

历史叙述文档包括 `src/engine/document/架构设计说明概要.md`、`src/engine/document/hook与触发层设计讨论结论.md`、`src/engine/document/WorldAreaSystem.md`。

ADR 规则的权威来源是 `docs/decisions/README.md`；写 ADR 前必须阅读。

满足以下任一条件时，先向用户提议新增 ADR，并等待确认：

- 跨越至少 2 个引擎顶层目录，或修改契约：`PipelineCatalog`、`EventCatalog`、`AttributeSchema`、`StatusTypeRegistry`、线程间协议、checkpoint 格式。
- 将已经实现的方案切换为另一种方案。
- 引入新的 registry、通信机制或分层方式。
- 建立未来 passive、skill、pipeline 必须遵守的约定。

不要静默修改已 `Accepted` 的 ADR 正文；实质修正应新增 ADR，并在新 ADR 中写 `Supersedes: NNNN`。ADR 使用中文书写。
