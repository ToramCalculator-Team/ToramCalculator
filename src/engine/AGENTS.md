# Engine — 代理工作指南

## 通信机制角色（权威定义）

引擎里所有「事件 / 通知 / 订阅」类机制必须归入以下两个角色之一，不要新增第三类通道。各机制类注释以本节为准。

| 角色 | 实现 | 时间方向与作用域 | 用途 | 不负责 |
|---|---|---|---|---|
| **跨帧投递** | `FsmMessageQueue`（归 `World` 持有） | 未来、定向（有目标成员） | 按模拟时间把尚未发生的成员 FSM 消息投递出去，取出即删 | 不做发布订阅、不广播、不产出对外数据 |
| **事件总线** | `EventBus`（归 `World` 持有） | 过去、广播（按作用域订阅） | 各过程自发发布「已发送的事实」；订阅决定哪些事实对外交付 | 不做跨帧投递、不构造 FSM 消息、不解释事实内容 |

两个角色的区别在本质上，不在名字上：**队列投递一个尚未发生的定向动作，总线广播一个已经发生的既定事实。** 前者到点被消费掉，是待办；后者被观察后仍在，是发布点。

派生信号一律视为「喂入某个角色的适配器」，不是独立机制：

- `StatusInstanceStore` 变更、`Pipeline.emit`、阈值穿越 → 发布到 `EventBus`。
- 外部控制器意图 → 经输入端口快照进入 `World`，由成员按目标身份标记接收。

**事实发布点唯一**：同一事实只能有一个发布点。权威结算点同时需要内部响应和外部观察时，发布一次即可——成员作用域与外部作用域是同一条总线上的两种订阅，不需要成对派发。两个发布点必然有一个被后续补充遗忘，而缺失在事后无法发现。

**意图入口不是事实发布点**：进入引擎的意图属于输入记录，向外的已发送事实属于事件总线，两者方向相反，不共用「事实」这个名称。

判据：若新机制是「按时间延迟触达 FSM」→ `FsmMessageQueue`；若是「让外部知道发生了什么」→ `EventBus` 发布。两者都不匹配时先提 ADR，不要私自加总线。

成员之间相互影响的写入不进队列也不立即施加，而是记入 Tick 内的阶段缓冲，由结算相统一交付。判据是写入目标：写自身的立即执行，写其他成员或共享集合的走阶段缓冲。

## 线程间通道

引擎与主线程之间的数据面只有两个端口，每端口一个共享缓冲区，不要新增第三个端口：

- **输入端口**：控制侧写自己的槽位，引擎每 Tick 读出一份输入快照。槽位内分状态区（方向、步态、强度）与命令区（离散动作），同槽位共用一个发布号。
- **输出端口**：引擎写。状态区承载成员与区域的连续世界状态、共享时间轴映射，逐 Tick 覆盖提交，读取方只取最新提交；事件区承载需要逐次消费的离散事实，按追加顺序写入，顺序以模拟时刻为主键、同 Tick 序号为兜底。两区在 Tick 末同一次提交中一起发布，共用一个提交号。

分区的不变量是**发布独立**，不是缓冲独立：容量与失败策略独立（状态区覆盖，事件区保留深度不足即失败）、消费者读取游标独立、每个端口只做一次布局校验与一次缓冲区交接。发布号的粒度由写入者数量决定：输入端口每槽位一个，输出端口全区一个 Tick 末提交号。

模拟时刻是采样刻度，不是事件时刻：Tick 内任意两个时刻的差值是设备性能的函数，不是领域事实。事实因此不携带 Tick 内时间戳，也不会「在 Tick 1 与 Tick 2 之间的某时刻发生」——一个事实属于某一 Tick，并在该 Tick 内排第 N 位。

控制面（生命周期命令与结果、一次性变长查询、运行故障）不走共享内存。

**没有订阅者时不产生任何对外数据**（ADR 0059）。订阅是显式声明：事件区未声明消费者时不创建也不写入；逐 Tick 状态历史未请求时不创建 Writer，也不承担共享内存环境门槛。无论有无订阅，模拟结果逐 Tick 一致——引擎不得为了满足订阅而改变模拟。

过线的只能是设备无关、已定帧、可重放的语义动作值：方向是世界方向，步态是语义标签（走 / 跑），命令不带墙钟时间。

引擎不持有任何外部回调，也不假设输出一定有消费者。

## 文档与 ADR

引擎设计意图通过模块旁的模块架构文档、`src/engine/document/` 和 `docs/decisions/` 保留。工作时读取相关文档；新设计内容写入项目级 ADR，历史叙述文档只作为历史快照读取。

历史叙述文档包括 `src/engine/document/架构设计说明概要.md`、`src/engine/document/hook与触发层设计讨论结论.md`、`src/engine/document/WorldAreaSystem.md`。

ADR 规则的权威来源是 `docs/decisions/README.md`；写 ADR 前必须阅读。

满足以下任一条件时，先向用户提议新增 ADR，并等待确认：

- 跨越至少 2 个引擎顶层目录，或修改契约：`PipelineCatalog`、`EventCatalog`、`AttributeSchema`、`StatusTypeRegistry`、线程间协议、checkpoint 格式。
- 将已经实现的方案切换为另一种方案。
- 引入新的 registry、通信机制或分层方式。
- 建立未来 passive、skill、pipeline 必须遵守的约定。

不要静默修改已 `Accepted` 的 ADR 正文；实质修正应新增 ADR，并在新 ADR 中写 `Supersedes: NNNN`。ADR 使用中文书写。
