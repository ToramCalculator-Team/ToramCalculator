# EventOutputFilter

## 模块职责

1. **订阅**：向事件源注册订阅，按事件名与主体筛选关注的事件。
2. **接收**：事件发布时同步接收，按订阅条件筛选。
3. **暂存**：把匹配事件按发生顺序写入自己的事件缓冲，保留事件负载与逻辑时刻。
4. **提交**：按声明在事件到达时或逻辑时刻完成边界发布提交号。
5. **容量与失败**：每个过滤器持有自己的读游标，已读区域才能被复用；容量不足时显形失败并上报。

## 理想结构

### 核心依赖

```typescript
class EventOutputFilter implements EventSink {
  // 订阅声明：事件名与主体筛选
  private readonly subscription: EventSubscription;

  // 事件缓冲：一个过滤器一个共享缓冲、一个提交号
  private readonly writer: EventBufferWriter;

  // 诊断
  private readonly stats: ObserverStats;
}
```

### 接口草案

```typescript
/**
 * 事件订阅声明
 *
 * 声明只含纯数据：事件源按事件名与主体筛选。
 * 复杂条件由事件源侧注册，不随声明跨线。
 */
interface EventSubscription {
  /** 订阅的事件名。 */
  readonly eventNames: ReadonlySet<string>;

  /** 按事件主体筛选的目标；省略时匹配该事件的全部主体。 */
  readonly subjectIds?: ReadonlySet<string>;
}

/**
 * 事件接收端
 *
 * 事件源把匹配的事件按发生顺序交给接收端；接收端负责自己的缓冲与容量策略。
 */
interface EventSink {
  /**
   * 接收一条事件
   *
   * @param event 领域事件
   * @param tag 事件发生的逻辑时刻
   */
  onEvent(event: DomainEvent, tag: Tag): void;
}

/**
 * 构造过滤器
 *
 * 用事件订阅声明与事件缓冲写入器构造实例，并向事件源注册订阅。
 *
 * @param subscription 事件订阅声明
 * @param writer 事件缓冲写入器
 */
constructor(subscription: EventSubscription, writer: EventBufferWriter)

/**
 * 接收事件
 *
 * 事件源在事实发布时同步调用；条件成立的事件按发生顺序写入自己的缓冲。
 *
 * @param event 领域事件
 * @param tag 事件发生的逻辑时刻
 */
onEvent(event: DomainEvent, tag: Tag): void

/**
 * 逻辑时刻完成
 *
 * 在逻辑时刻结束时调用，提交本批次事件的提交号。
 *
 * @param tag 已完成的逻辑时刻
 */
onTagComplete(tag: Tag): void

/**
 * 过滤器诊断
 *
 * @returns 接收次数、写出耗时、容量使用与失败计数
 */
getStats(): ObserverStats

/**
 * 释放
 *
 * 取消事件源订阅并释放缓冲写入器。
 */
dispose(): void
```

```typescript
/**
 * 事件缓冲写入器
 *
 * 每个过滤器一个共享缓冲与一个提交号；事件逐条追加，已读区域才可复用。
 */
interface EventBufferWriter {
  /**
   * 追加一条事件
   *
   * @param event 领域事件
   * @param tag 事件发生的逻辑时刻
   */
  append(event: DomainEvent, tag: Tag): void;

  /**
   * 发布提交号
   *
   * 读取方按提交号与读游标判断可读范围。
   *
   * @param tag 提交对应的逻辑时刻
   */
  commit(tag: Tag): void;
}
```

### 事件流

```text
事实成立
  → 事件源发布事件
  → EventOutputFilter 按订阅筛选
  → 写入自己的事件缓冲
  → 提交边界发布提交号
```

事件在事实发生时进入过滤器，由发布驱动，不通过周期扫描发现。动态创建的事件源由事件源自身维护订阅，过滤器不逐个事件源重建。

### 提交与顺序

写入可在事件到达时立即提交，也可在逻辑时刻完成时批量提交；批量提交只决定跨线程发布边界，不改变事件的发生时间和顺序。

过滤器保留事件的逻辑时刻、同一时刻内的确定顺序、事件名称与负载。需要多个事件源的全序时，顺序规则由网络因果顺序或稳定主体顺序给出，不依赖容器遍历顺序。

### 生命周期

订阅建立后过滤器开始接收事件；取消订阅或 `dispose` 后停止接收并释放写入器。订阅声明是纯数据，跨线程时由共享编解码器按版本校验；共享缓冲由创建方按布局分配，两侧分别派生校验。

## 关键设计决策

### 1. 事件由事件源驱动

**设计理念**：事件的发生时刻由事实决定，不由采样节奏决定。

过滤器订阅事件源，在发布时接收；它不扫描状态推导事件，也不持有自己的定时器。

### 2. 提交只决定跨线程边界

**设计理念**：事件的发生时间、顺序与负载不因提交方式改变。

事件在事实发生时同步进入过滤器；提交可以逐事件进行，也可以在逻辑时刻完成时批量进行。批量提交只决定读取方何时看到这批事件。

### 3. 一个过滤器一个读游标

**设计理念**：离散事件必须逐次消费。

每个事件过滤器持有自己的共享缓冲与读游标，已读区域才能被新事件复用，未读事件不被覆写。容量不足时显形失败并上报。

### 4. 订阅声明是纯数据

**设计理念**：跨线程只传可校验、可版本化的数据。

订阅声明包含事件名与主体筛选，不携带函数、对象引用或表达式；需要复杂条件时由事件源侧注册，不随订阅声明跨线。

### 5. 事件源是直接依赖

**设计理念**：过滤器的职责是筛选与写出，事件从哪里产生由事件源负责。

过滤器只通过订阅声明与事件接收端接口工作，不感知事件源内部结构，也不改变事件的产生与内部响应。
