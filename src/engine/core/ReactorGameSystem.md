# ReactorGameSystem

## 模块职责

ReactorGameSystem 是 [GameSystem](GameSystem.md) 的 Reactor 实现，把网络装配、输入采样与状态发布映射到运行库的 tag 与微步上。

1. **网络根**：作为 `App` 的子类，持有游戏层构建的反应器网络。
2. **输入采样**：持有输入采样器，把输入通道接到网络。
3. **状态对象**：维护统一状态对象，每一步执行完毕后更新。
4. **时刻映射**：把运行库的 tag 映射为逻辑时刻，报告已完成时刻与下一项工作时刻。
5. **状态编解码**：把 `App` 的内部状态转换为可序列化的状态数据，并从状态数据恢复。
6. **自有调度**：持有自己的调度时钟，把它安装为运行库的物理时间源，并接管运行库内部的等待与立即唤醒入口；把宿主转发的启动、暂停、恢复与单步映射到调度操作。

## 理想结构

```typescript
abstract class ReactorGameSystem extends App implements GameSystem {
  /** 网络根：子类构建的反应器网络。 */
  protected root!: Reactor;

  /** 输入采样器：网络内的源反应器。 */
  protected inputSampler!: InputSampler;

  /**
   * 调度时钟：本实现的虚拟时间与受控唤醒。
   *
   * 它同时是运行库的物理时间源，并接管 App 的等待入口（受控 `_alarm`）
   * 与立即唤醒入口；不新增与等待机制并行的第二套时钟，宿主也不持有它。
   */
  private readonly scheduler!: SchedulerClock;

  /** 统一状态对象。 */
  public abstract readonly state: SystemState;
}
```

```typescript
/**
 * 建立网络与状态对象
 *
 * 由构造函数调用。创建调度时钟并接管运行库的时间入口，建立网络根与输入采样器、分析反应依赖，并完成起始时刻的启动反应。
 *
 * @param input 输入通道
 * @param state 既有状态；恢复时提供
 */
protected abstract initialize(input: InputChannel, state?: unknown): void

/**
 * 建立网络根与输入采样器
 *
 * @param input 输入通道
 * @returns 网络根与输入采样器
 */
protected abstract createNetwork(input: InputChannel): {
  root: Reactor;
  inputSampler: InputSampler;
};

/**
 * 当前逻辑时刻
 *
 * @returns 运行库当前 tag 映射出的时刻；微步写入 cursor
 */
getCurrentTime(): SimulationTime

/**
 * 下一项工作的逻辑时刻
 *
 * @returns 事件队列队首 tag 映射出的时刻；队列为空时返回 null
 */
getNextTime(): SimulationTime | null

/**
 * 捕获状态
 *
 * 把 App 检查点转换为只含原始值的状态数据：起始时刻、当前 tag 与微步、待处理事件。
 *
 * @returns 当前时刻与检查点 payload
 */
captureState(): { time: SimulationTime; payload: ReactorCheckpointPayload }

/** 停止调度，释放接管的时间入口、网络、输入采样器与事件源订阅。 */
dispose(): void
```

### 时刻映射

`SimulationTime.cursor` 放微步：外部按 `timeMs` 排序，需要精确定位时用 `cursor`。

### 状态对象

状态对象由网络发布的参数与实体状态派生，每一步执行完毕后整体更新。网络在同一个逻辑时刻上可能有多个微步；状态对象在该时刻的全部微步完成后才更新，读取方因此不会拿到上游已完成、下游未完成的中间状态。

### 状态数据与恢复

恢复通过构造参数完成：提供状态数据时，在启动任何工作之前把 payload 还原为 `App` 检查点。运行库不重跑启动反应，也不重排同一批定时器。

### 时间与唤醒

本实现持有自己的调度时钟，并接管运行库的全部运行时时间入口。运行库的时间能力只有一个读取入口和两个真实唤醒入口，本实现分别接管：

| 运行库入口 | 本实现的接管方式 |
|---|---|
| 物理时间读取（时间门、起始时刻、物理 Origin、reaction deadline、reaction 内的经过时间） | 把调度时钟安装为运行库的物理时间源 |
| 等待（App 的 `_alarm`，由 `_setAlarmOrYield` 安排、`_cancelWakeups` 与 `_cancelNext` 取消） | 替换为受控 `_alarm`，唤醒由调度时钟交付 |
| 立即唤醒（物理时间已越过 tag 时用于补算的立即调用） | 覆盖立即唤醒入口，由调度时钟安排；取消路径一并清理 |

这三处是当前运行库版本的完整清单。接管完成后，运行库调度路径不再直接读取真实时间，也不再有库内的全局定时器。物理时间读取与唤醒安排共用同一份时间状态，因此倍速、暂停与恢复不会让"读到的现在"和"下一次唤醒"分叉。

时钟前进时，到期的唤醒按先后顺序触发。时钟不前进时运行库没有到期工作，系统停在当前已完成的时刻。

运行库提供启动、暂停、恢复、单步与停止入口。宿主把这些生命周期命令转发给本实现，由本实现映射到调度时钟的启动、停住与拨动；宿主不创建、不持有、不操作这个时钟。调度时钟的归属决策见 [ADR 0062](../../../docs/decisions/0062-host-does-not-own-scheduling-clock.md)。

## 关键设计决策

### 1. 实现是 App，契约不依赖 App

**设计理念**：单继承留给运行库。

契约只描述时刻报告与状态发布；本实现把契约映射到 `App` 的 tag、微步与检查点能力。其他模型实现同一契约时不受 `App` 影响。

### 2. 时刻由 tag 映射

**设计理念**：tag 是运行库的唯一顺序轴，逻辑时刻是它对外的表达。

`timeMs` 表达逻辑时刻，微步写入 `cursor`；外部按 `timeMs` 排序，需要精确定位时用 `cursor`。

### 3. 状态对象由网络派生

**设计理念**：可观察内容由网络装配与游戏内容决定，只有实现能完整描述。

状态对象按系统的内部结构组织；读取方需要什么形状，由读取方自行投影。

### 4. 物理时间读取本实现的调度时钟

**设计理念**：物理时间就是系统所在虚拟世界的真实时间。

调度时钟由本实现持有；物理 Origin 事件与经过时间计算据此取值。宿主只提供平台能力，不控制该时钟。

### 5. 恢复通过构造

**设计理念**：恢复与首次运行走同一条路径。

状态数据在构造函数中还原，之后才允许启动工作；运行库因此只面对位于给定时刻的实例。

### 6. 宿主不持有调度时钟

**设计理念**：调度属于模拟实现，宿主只承担生命周期编排。

调度时钟由本实现创建、持有和停止；宿主通过生命周期命令影响推进，不直接操作时间源。

### 7. 时间源与唤醒源是同一个调度时钟

**设计理念**：单一事实源优于读取与等待各自维护时间状态。

倍速、暂停与恢复必须同时作用于"读到的现在"和"安排的下一次唤醒"。拆成两个对象会出现时间与唤醒不同步；因此调度时钟既作为物理时间源，也接替运行库内部的等待与立即唤醒。

### 8. 运行库的时间入口清单是模块边界

**设计理念**：接管完整性决定暂停与恢复是否真的停住模拟。

等待入口与立即唤醒入口是实现字段与 protected 方法，不是运行库的稳定契约。本模块依赖的入口清单只应包含"物理时间读取、等待、立即唤醒"三项；运行库新增任何时间或定时器入口时，必须重新核对本清单并补测试，否则会出现暂停失效或空转唤醒。接管完整性以暂停、恢复、倍速、单步、销毁的契约测试，以及"调度路径不触发全局定时器与真实时间读取"的断言为准。
