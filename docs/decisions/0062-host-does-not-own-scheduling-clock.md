# 0062 - 宿主不持有调度时钟

- **状态**: Accepted
- **日期**: 2026-11-23
- **决策层**: 引擎（宿主与游戏系统边界）
- **相关代码**: `src/engine/core/GameSystemHost.ts`、`src/engine/core/GameSystem.ts`、`src/engine/core/Reactor/ReactorGameSystem.ts`、`src/engine/core/PausableHostClock.ts`

## 决策问题

宿主到底该不该持有一个自顾自运作的时间源，并经由控制这个时间源来暂停、恢复和倍速游戏系统？

## 决策驱动

- 宿主职责要稳定、边界要清晰，不因游戏系统内部的调度方式而改变。
- 模拟精度和性能都要考虑。

## 候选方案

### A. 宿主持有一个"自顾自运转"的时钟

时钟只依赖真实经过时间与倍率前进，游戏系统把唤醒登记给它。

- 优点：时钟独立于游戏系统；宿主冻结时钟就能结构性暂停，不依赖游戏系统实现是否自觉。
- 缺点：存在**性能与仿真保真度的取舍**。节拍细，唤醒及时、仿真保真度高，但空闲时也持续占用事件循环；节拍粗，空闲开销低，但唤醒延迟变大、仿真保真度下降。两者无法同时最优。

### B. 宿主持有事件驱动的时钟

时钟根据游戏系统登记的到期时刻安排真实定时器，空闲时不唤醒。

- 优点：空闲开销低，唤醒延迟接近真实定时器精度，性能和保真度都更好。
- 缺点：时钟的真实唤醒安排**依赖游戏系统的调度信息**，两者产生关联。由宿主拥有这样的时钟，等于让宿主持有游戏系统调度机制的一部分，职责边界不清晰。

### C. 宿主不持有时钟，只转发生命周期控制事件（本决策采用）

时钟和调度循环属于游戏系统的实现；宿主只接收并转发暂停、恢复、单步、停止等生命周期命令，同时提供平台能力。

- 优点：**对比 A 性能更好**（游戏系统可以采用事件驱动，空闲不唤醒）；**对比 B 职责边界更清晰**（时钟属于系统调度实现，宿主不参与）；宿主形态不随调度实现变化。
- 缺点：暂停/恢复的保证从"宿主冻结环境"变成"游戏系统实现遵守契约"，需要契约测试兜底；宿主无法再统一提供时间查询、倍速等能力；"唯一时钟"下沉为系统实现内部的不变量。

## 决议

选择 C：**宿主不持有调度时钟；时钟归游戏系统的调度实现，宿主只转发生命周期控制事件并提供平台能力。**

- 宿主不创建、不持有、不操作调度时钟。暂停、恢复、单步、倍速由游戏系统实现映射到自己的调度循环。
- 选择 C 的理由有两面：相对 A，它摆脱了"性能与仿真保真度只能取其一"的取舍；相对 B，它把时钟与调度留在系统实现内部，宿主不触碰游戏系统的调度信息，边界更干净。
- 这个选择不代表 A 或 B 不可行。A 在需要宿主结构性兜底暂停时仍然可用；B 在能接受宿主持有调度机制的场合也成立。本决策只是判断当前系统更适合 C。
- 暂停语义由游戏系统契约定义：暂停后真实时间流逝不改变已完成逻辑时刻、不触发任何工作；恢复从暂停点继续，不补算暂停期间的真实时间。
- 宿主职责收敛为：构造与承载游戏系统、提供平台能力（真实时间源、输入通道、共享内存等）、生命周期编排、观察者接入、命令与结果、销毁。
- "唯一时钟"是游戏系统实现内部的不变量，不是宿主提供的环境对象。
- 明确排除：本决策不规定驱动算法、消息协议与观察者实现，也不把宿主自身的真实时间工具（遥测、命令超时）并入游戏系统的调度时钟。

## 代价

- 失去结构性暂停保证：宿主不能仅凭冻结环境停止系统，必须依赖每个实现遵守暂停契约；实现违约只能由契约测试暴露。
- 宿主层不再统一提供当前时刻、倍速等时间能力，跨实现一致性需要契约扩展与测试保证。
- "唯一时钟"无法由宿主机械校验，复杂度下沉到系统实现。
- 现有宿主、游戏系统实现、模块文档与测试需要一起迁移；过渡期存在两套形态短暂并存的协调成本。
- 不同实现可以选择不同的时间精度与驱动策略，宿主层无法给出统一性能特征。

## 重新评估条件

- 目标运行时出现可暂停、可倍速且无空闲唤醒成本的独立时间源，使 A 同时满足性能与保真度。
- 同一线程需要多个游戏系统共享单一时间轴或统一倍速，而系统自持时钟无法协调。
- 游戏系统自持时钟在多个独立实现中反复违反暂停/恢复契约，说明契约约束不足。
- 宿主需要跨实现统一的时间查询或倍速命令，且现有契约扩展无法承载。
