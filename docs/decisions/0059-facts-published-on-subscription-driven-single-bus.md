# 0059 - 事实发布与订阅驱动的事件观察

- **状态**: Accepted
- **日期**: 2026-10-14（2026-11-11 修订）
- **决策层**: 跨层（引擎 / 通信 / 应用）
- **相关代码**: `src/engine/core/Event/`、`src/engine/core/Reactor/OutputCollector.md`、`src/engine/core/ReactorGameSystem.md`
- **相关决策**: 修订并取代原“唯一引擎级事件总线”方案

## 决策问题

模拟过程中会发生领域事实，例如伤害结算、状态变化和执行链完成。GameReactor 内部组件需要对部分事实作出同步响应；外部消费者可能需要筛选并记录其中一部分。需要明确事实由谁发布、内部响应与外部观察如何连接，以及没有观察订阅时事件如何处理。

Reactor 网络中的数据依赖由 Reaction 与端口构成 DAG。动态创建的成员会改变事件生产者集合，不适合要求每个成员在静态 DAG 中连接到统一外部过滤器。外部事件观察需要订阅事件生产者的事实流，同时保持在 Reactor 网络之外。

## 决议

事实由有权确认事实成立的执行过程显式发布到所属 GameReactor 的本地 EventBus。EventBus 在当前调用中按订阅同步分发事件及其负载，不保存已发布事件，不创建 tag，也不调度未来操作。

内部逻辑订阅和外部观察是本地 EventBus 的不同订阅者：

- FSM、BTRuntime、buff 等模拟逻辑可按事件目录订阅事实，并同步响应。此类订阅属于模拟行为。
- 外部 `EventOutputFilter` 是网络外观察订阅者，依据消费者配置订阅相关 GameReactor，按事件规则筛选，并将匹配事件追加到自己的有界输出批次。
- 没有匹配订阅者时，事件在同步发布完成后自然结束，不排队、不覆盖上一事件，也不进入历史记录。之后建立的订阅者不会收到过去事件。
- 输出过滤器可在事件到达时立即写出，或先暂存并在 tag 完成时批量提交。批量提交只确定跨线程发布边界，必须保留每条事件的模拟时刻和确定顺序，不把事件采集改成周期扫描。
- 事件输出容量不足、SAB 写入失败等情况必须显式报告，不得静默丢弃已经被外部订阅接受的事件。
- 只有需要参与 Reactor 网络计算的数据依赖才使用 Reaction 与端口。事件输出过滤器不接入 Reactor DAG。

## 输出设施的生命周期

引擎提供 `OutputCollector`、`EventOutputFilter`、SAB writer 与诊断接口的通用机制。消费者通过输出配置声明需要哪些数据；GameSystem 在运行装配时据此创建对应实例并绑定缓冲区。未声明的设施不创建。

参数采集器和事件过滤器保持不同的触发语义：

| 设施 | 输入 | 触发 | 语义 |
|---|---|---|---|
| `OutputCollector` | Reactor 网络发布的连续参数 | 消费者配置的采样周期 | 求值或外推状态样本，允许按协议跳过中间样本 |
| `EventOutputFilter` | GameReactor EventBus 发布的离散事件 | 事件发布时同步触发 | 筛选并逐条保留匹配事件，不可静默覆盖或丢弃 |

两类设施共享宿主管理、SAB 写入协议和诊断基础设施，不合并为同一种采集语义。改变外部输出配置不改变模拟状态；内部 EventBus 订阅仍按模拟逻辑执行。

动态 GameReactor 由其生命周期管理者在创建时接入当前已启用的外部事件订阅，销毁时取消订阅。该注册关系是网络外观察订阅，不改变 Reactor DAG。

## 事实与负载

事件表示已发生的事实。事件目录定义名称、主体和负载 schema；事实确认过程在发布时提供事件负载。负载可以包含理解该事实所需的结果值，不应依赖可变 blackboard 的后续状态来重建事件发生时的结果。

执行链到达 `SUCCESS` 或 `FAILED` 终态后，`BTRuntime` 可发布执行链完成事实及结果负载。节点 entered/succeeded/failed 等运行时生命周期观测与领域事实区分建模，只在诊断或外部观察配置需要时产生。

拒绝结果若是消费者需要观察的领域事实，可以作为明确的事件发布；其名称与负载由事件目录定义。

## 代价与约束

- 内部订阅者同步执行，发布点和 handler 必须遵守模拟线程的同步约束；需要未来执行的响应应提交 Reactor `Action.schedule`。
- 外部过滤器需对目标 GameReactor 集合管理订阅句柄。成员创建、销毁和消费者卸载必须正确建立与清理订阅。
- 单次发布期间的订阅集合变更语义必须由 EventBus API 明确，避免迭代中新增或取消订阅造成不确定分发。
- 外部事件的确定顺序来自模拟执行顺序；跨 GameReactor 的同一 tag 顺序以及多个生产者并发场景需由宿主执行模型明确定义。
- 输出批次需要有界容量、提交边界、失败传播和检查点策略。EventBus 本身不承担这些存储职责。
- 内部事件负载属于模拟逻辑输入；外部事件输出只是订阅者对同一事实的观察，不得回写模拟状态。

## 重新评估条件

- 需要让事件在没有订阅者时仍可供未来订阅者读取。
- 需要跨 Reactor 延迟路由、可靠重试或独立于当前模拟线程的异步处理。
- 事件输出的容量、检查点或顺序契约不能由网络外 EventOutputFilter 满足。
- 参数样本和事件记录出现必须统一提交原子性的新需求。
