# 0052 - 高频世界状态统一使用实时状态 SAB

- **状态**: Accepted
- **日期**: 2026-08-15
- **决策层**: 跨层（引擎 / Worker / Session / UI / 渲染）
- **相关代码**: `src/engine/core/thread/`、`src/engine/core/World/Member/`、`src/engine/core/World/Area/`、`src/features/simulator/session/`、`src/platform/render/scene/`
- **相关 ADR**: Refines 0050；Depends on 0029；Depends on 0044

> 2026-08-20 修订：将本文收敛为实时状态所有权、连续状态与离散事件的通道边界，以及逻辑事实与视觉资源的职责边界；删除字段、表结构、容量、公式、轨迹变体和迁移步骤等实现细节。动态视觉表现由渲染层结合逻辑状态、逻辑时间和本地资源计算，本文不规定其具体载体。

## 决策问题

引擎 Worker 同时向 UI 和渲染层提供高频世界状态。若不同消费者各自维护传输路径或状态副本，就会产生重复状态源、重复序列化和不同的消费节奏。

渲染层还需要模型、材质和动画映射等静态视觉资源。该信息不属于实时世界状态，不能因为实体在运行中出现就重复通过高频通道传输。系统需要区分静态资源、实体使用的资源引用和实体运行状态。

系统需要决定：是否继续为不同消费者和状态类别维护多条高频路径，还是把连续世界状态统一放进一个由 Worker 写入、UI 与渲染层共同读取的 latest-state 共享通道，同时保留离散事件与完整历史的独立语义。渲染层本身不需要通过跨线程视觉事件回放来建立当前世界。

## 决策驱动

- Worker 必须是实时世界事实的唯一写入者，UI 和渲染层不能各自维护一份高频权威状态。
- UI 和渲染器都只需要最新状态，可以跳过中间 Tick；把这些状态排队会产生过期对象和重复结构化克隆。
- 渲染器的静态视觉资源应由本地注册表或一次性资源清单提供；实时状态只携带可解释当前实体的稳定资源引用，不重复传输模型 URL、材质和动画映射。
- 实时状态的具体组成会随场景装配和领域能力变化，协议必须允许在生命周期边界协商其解释方式。
- 区域是世界实体，但与成员的属性、生命周期和渲染职责不同，不能被当作成员的附属字段或视觉对象。
- 逐次消费的技能、状态和用户动作不能因为 SAB 覆盖而丢失；完整 Tick 历史也有独立的长期生命周期和容量策略。

## 候选方案

### A. UI 使用消息快照，渲染层使用独立世界状态 SAB

- 优点：可以沿用当前 UI 接口，渲染位置读取路径改动较小。
- 缺点：成员状态被重复编码；属性和区域仍走消息对象；UI 与渲染器可能读取不同 Tick 的事实；后续继续增加第三条高频路径的概率很高。

### B. 连续世界状态统一使用一个 latest-state SAB，离散事件和 Tick 历史保持独立

- 优点：Worker 只写一次，UI 和渲染器共享同一个提交版本；中间状态可以自然跳过；成员属性、modifier 和区域可以按场景布局；历史数据不污染实时 ABI。
- 缺点：需要协商布局、管理容量和版本；UI 需要本地轮询或调度器把 SAB 提交版本转换为响应式更新；共享内存需要安全上下文和跨源隔离。

### C. 所有跨线程数据，包括离散事件和 Tick 历史，都进入同一个 SAB

- 优点：跨线程载体单一，理论上可以减少消息类型。
- 缺点：覆盖式 latest-state 无法表达事件逐次消费；事件队列和完整历史的生命周期、容量与重放语义不同；把三种语义强行放进同一个 ABI 会增加丢失、回收和版本迁移风险。

## 决议

选择 B：**成员和区域的连续世界状态统一写入由 Worker 拥有的实时状态 SAB；UI 与渲染层只读取同一份 latest-state 提交，渲染层使用本地静态资源解释逻辑事实；离散事件和完整历史继续使用各自语义的独立通道，渲染层不依赖跨线程视觉事件建立当前表现。**

### 连续状态的职责边界

实时状态共享通道只承载能够从当前提交重建世界的连续逻辑事实，例如实体活动状态、空间状态、逻辑动作状态和区域状态。具体字段、布局、容量和版本协商属于代码契约与实施文档，不在本 ADR 中规定。

渲染器的输入分为两类：

1. **静态视觉资源**：由渲染侧或会话初始化阶段提供，包含模型、外观和动画映射等资源定义，不进入实时状态共享通道。
2. **连续逻辑状态**：由 Worker 统一写入，UI 与渲染层读取同一份最新提交。渲染器依据逻辑状态、逻辑时间和本地资源计算当前帧表现，包括需要动态推进的阶段进度；逻辑层不携带材质、网格、粒子或动画播放指令。

已经结束且未被读取到的瞬时状态不补播；如果未来需要逐次回放，必须重新评估连续状态与离散事件的边界。

确立以下不变量：

1. Worker 是连续世界事实的唯一写入者；UI 和渲染层只读同一份最新提交，并可以跳过中间提交。
2. 成员、区域和其他连续实体状态在语义上保持独立，不能为了复用传输结构而抹平领域边界。
3. 实时通道的布局、容量和兼容性必须在明确的生命周期边界协商；超出协商能力时应显形失败，不能静默覆盖或截断事实。
4. modifier 来源和其他可追溯逻辑事实属于逻辑状态的一部分，但其具体编码方式由代码契约决定。
5. 连续状态共享通道不承载逐次事件。技能触发、攻击、受击、死亡、目标切换和用户输入确认等事件按各自语义进入独立事件通道。
6. 渲染器不依赖跨线程视觉事件建立当前表现；它从一致的连续状态提交和本地资源映射重建当前世界。
7. 完整模拟 Tick 序列和历史分析数据不与 latest-state 连续状态合并，继续遵循独立的历史生命周期。
8. 是否建立实时状态投影由会话显式决定；普通引擎执行不因读取需求而隐式改变自身生命周期。

### 明确排除

- 不为 UI 和渲染层分别维护高频权威状态。
- 不把事件队列编码成可以被覆盖的 latest-state 状态。
- 不把静态视觉资源定义或逐帧视觉命令写入连续状态通道。
- 不要求渲染器通过历史事件回放来建立当前世界。
- 不以备用视觉事件通道掩盖连续状态协议的缺失。
- 不把不同领域实体强行塞进同一种语义模型。
- 不把实时最新状态和 Tick 历史合并为同一生命周期。

## 代价

- Worker 和消费者必须协商共享状态的解释和生命周期；协议变化需要同步迁移。
- UI 不会因共享状态写入自动获得应用层响应式更新，需要本地调度把最新提交转换为界面状态。
- 逻辑状态中的属性、来源和区域事实需要可解释的编码与解码契约。
- 共享状态具有有限容量；超限场景必须失败或重新协商，不能依赖无限增长。
- 实时功能继续要求共享内存可用、跨源隔离和安全上下文；不为该能力增加隐式消息降级路径。
- 迁移期间需要同时验证静态资源、实体生命周期、UI、渲染器和 Worker 生命周期；旧的高频权威路径不能长期与新路径双写。
- 渲染器不会补播它未读取期间已经结束的动作；如果未来产品要求逐次展示这类瞬时效果，需要重新评估本决策，而不是增加隐式事件旁路。

## 重新评估条件

- 代表性场景中共享状态容量或协商成本使拒绝成为正常业务路径。
- 运行时开始支持成员或属性的高频动态创建，生命周期边界替换 SAB 无法满足延迟预算。
- UI 或渲染器需要跨会话、跨进程或远程消费实时状态，Session 内共享内存不再覆盖主要生命周期。
- 测量显示共享状态的读取调度、数据解释或跨源隔离环境门槛成为主要性能或可用性瓶颈。
- 平台提供新的零复制 latest-state 机制，同时具备等价的一致性和生命周期能力。
- 产品明确要求渲染器逐次展示当前状态之外的瞬时动作或视觉效果。
