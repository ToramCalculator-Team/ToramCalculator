# 0060 - 运行记录以模拟时间为权威顺序轴

- **状态**: Accepted
- **日期**: 2026-10-14
- **决策层**: 跨层（引擎 / 通信 / 分析）
- **相关代码**: `src/engine/core/tickStateHistory.ts`、`src/engine/core/runOutput.ts`、`src/engine/core/thread/protocol.ts`、`src/engine/core/thread/worldStateBuffer.ts`
- **相关 ADR**: Refines 0034；Refines 0044；Depends on 0059

> 2026-10-20 修订：把「同刻序号」改名为「同 Tick 序号」，并补上模拟时刻是采样刻度而不是事件时刻的说明。原用词暗示同一模拟时刻内存在可比时刻，而 Tick 内没有可观测的时间点；决议本身（以模拟时间为权威顺序轴、帧序号只用于定位）未变。

## 决策问题

一次运行会产生多类需要跨线程保留的记录：逐 Tick 状态历史、已发送的事实、输入记录。这些记录必须在运行结束后按时间回溯，并支持两次不同配置的运行互相比对。

当前记录以帧序号作为主键与寻址依据。帧序号由逻辑频率决定，同一批真实事实在 30Hz 与 60Hz 下会得到不同的帧编号。需要决定运行记录以什么作为权威顺序轴，以及帧序号在记录中承担什么职责。

## 决策驱动

- 帧序号把采样密度和事实时刻绑定在一起，改变逻辑频率会拉伸或压缩同一批事实的间隔。
- 记录必须能精确回溯到具体时刻，不能用抽稀、降频或静默丢弃换取性能。
- 同一模拟时刻内可能产生多条事实，需要确定的相对次序。
- 逐 Tick 记录本身是等间隔采样网格，按需寻址需要精确而稳定的整数标识。
- 顺序轴与寻址标识承担不同职责，混用会让两者都不可靠。

## 候选方案

### A. 帧序号作为权威顺序轴

- 优点：与引擎内部推进单位一致，寻址天然是整数，读取接口直观。
- 缺点：跨逻辑频率不可比；帧序号把采样密度当成时刻，改频率即改变记录的领域含义；无法表达「不早于某时刻」这类与原频率无关的查询。

### B. 模拟时间作为权威顺序轴

- 优点：模拟时间是物理量，与帧率无关，跨运行可按同一尺度比对。
- 缺点：模拟时间是浮点累加量，直接作为寻址键在相等比较上不可靠；需要额外的整数标识承担按需寻址。

只记录当时真实可行且实际考虑过的方案。

## 决议

选择 B：**运行记录的权威顺序键是模拟时刻与同 Tick 序号；帧序号只用于定位与诊断。**

- 记录不保存帧序号作为顺序依据。帧序号表达采样密度，不能用于推导持续时间或决策间隔。
- 事实记录的顺序键是模拟时刻，同 Tick 序号用于同一时刻内多条事实的定序。模拟时刻是采样刻度，不是事件时刻：Tick 内任意两个时刻的差值是设备性能与调度抖动的函数，不是领域事实，因此记录中不存在比 Tick 更细的时间划分。
- 逐 Tick 状态历史的顺序轴同样是模拟时刻，但它的采样序号是整数，继续承担分段覆盖校验与按需寻址。**顺序轴与寻址标识是两件事，不被合并**：记录按时间解释，读取按采样序号定位。
- 跨运行的时刻对齐必须由显式约定完成（锚点加步长，或量化到确定分辨率），不得依赖浮点相等。
- 记录读取接口接受模拟时刻语义的查询，由实现换算为采样序号；调用方不直接以浮点时间做相等匹配。

## 代价

- 需要同时维护模拟时间与采样序号两个标识，并明确各自职责，实现比单一帧序号复杂。
- 模拟时间是浮点累加量，跨运行取「同一时刻」需要约定量化方式；量化分辨率成为记录契约的一部分。
- 既有按帧序号寻址的记录读取接口需要迁移，分析侧的查询表达需要改写。
- 逐 Tick 状态历史的目录元数据需要携带时间锚点，不能只有帧范围。

## 重新评估条件

- 引擎规则时间不再以单调模拟时间表达。
- 引擎支持连续时间事件调度，使等间隔采样网格不再是记录的天然结构。
- 逻辑频率在单次运行内可变，使「锚点加步长」的时刻对齐不再成立。
